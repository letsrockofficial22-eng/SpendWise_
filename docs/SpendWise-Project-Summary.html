What SpendWise is

SpendWise is a personal finance and expense-tracking application designed around everyday student spending in Bangladesh. It records income and expenses in Bangladeshi taka (BDT), tracks daily and monthly budgets, turns transactions into charts and reports, and bundles practical tools: loans to repay or money lent, recurring bills, shared expense splits, monthly summaries, and full-account backup and restore.

It runs as a responsive web app built with Next.js, React, and TypeScript, and as an Android app packaged with Capacitor. Supabase supplies authentication and cloud PostgreSQL storage. The app is deliberately offline-first: each signed-in account has a local snapshot in IndexedDB, edits are shown immediately, queued, and synchronized when a connection returns.

Who it is for

SpendWise is aimed at students and young adults who want a lightweight, friendly way to understand daily cash flow. The interface is written for that audience — “Student account”, “Pocket money”, campus-oriented categories, and a calm, low-pressure visual tone. The default time zone is Asia/Dhaka, and the only supported currency is BDT.

Status: the application code, database migrations, and Android wrapper are present. To use it with real data, you must create your own Supabase project, apply the three migrations, set the two public environment variables, and verify Row Level Security with two real accounts. The repository alone does not connect to a Supabase project.

04 · Feature details

Accounts & access

A password-based account system built on Supabase Auth, with a web confirmation flow and a dedicated Android deep link.

01

Email/password registration with identity

Implemented

The sign-up form collects first name, last name, email, and a password of at least six characters. Both names are required before the request is sent.

  • Stored metadata: Supabase receives first_name, last_name, and a combined full_name.
  • Profile creation: a database trigger creates the profile row and copies the sign-up name, truncated to 100 characters.
  • Confirmation redirect: web signs up redirect to /auth/confirm; Android uses spendwise://auth/confirm.
  • No duplicate-name logic: names are display data, not unique identifiers — the email is the account key.
02

Sign-in with show/hide password

Implemented

Returning users sign in with email and password. A password-visibility control switches between masked and plain text and announces its state to assistive technology.

  • Safe redirect: an optional ?next= target is accepted only when it starts with a single / — protocol-relative and backslash paths are rejected.
  • Error handling: failures are shown inline; verification and credential problems are not leaked as account-existence details.
  • Session: Supabase manages the session; the app routes to the dashboard on success.
03

Email confirmation for web and Android

Implemented

The /auth/confirm page accepts every confirmation shape Supabase can return and exchanges it for a session.

  • PKCE code: ?code= is exchanged with exchangeCodeForSession.
  • Token hash: ?token_hash=&type= is verified with verifyOtp for signup, invite, magic link, recovery, email change, and email.
  • Hash tokens: access and refresh tokens in the URL fragment are installed with setSession.
  • URL hygiene: after success the query/hash is removed with history.replaceState.
  • Android: the native runtime catches spendwise://auth/confirm links and forwards them to the confirmation page.
04

Protected workspace and session handling

Implemented

All personal pages are guarded in the client store. If no valid session exists, the user is redirected to sign-in with a reason code and personal data is cleared from memory.

  • Auth listener: onAuthStateChange reacts to sign-in and sign-out, clearing state and protecting against account switching.
  • Defense in depth: UI guards are convenience only — Row Level Security is the real boundary for every read and write.
  • Session timeout: session checks are wrapped with a timeout so a stalled network call does not hang the workspace.
05

Offline session restore

Implemented

After a successful sign-in, the account ID is remembered locally. If the app is opened without a connection, the cached account is restored instead of forcing a login that cannot complete.

  • Conditions: a remembered account, a readable local snapshot, and a network/session failure. First sign-in still requires the internet.
  • Sign-out: clears the remembered account pointer, so a shared device does not reopen the previous workspace.
  • Expired sessions: canRestoreOfflineSession allows offline access while the device is disconnected, while online failures still require a valid session.

Dashboard & insights

The first screen answers four questions: what do I have, what did I spend today, how is my budget doing, and where is the money going?

Overview dashboard with selectable date

Implemented

Transactions

The core ledger: enter money in and out quickly, find any record, and take the filtered view with you as a spreadsheet.

12

Add income or expense

Implemented

One form handles both directions, with validation before anything is saved.

  • Amount: required, greater than zero, at most two decimals; quick buttons for ৳10, ৳20, ৳50, and ৳100.
  • Type: Expense or Income. Switching to income suggests “Pocket money”; switching back restores “Food & Drinks”.

Edit and delete with confirmation

Implemented

Every row exposes edit and delete controls. Editing opens the same form prefilled; deleting opens a modal that names the transaction and warns that removal is permanent. Both actions update the local snapshot first and queue a sync.

Implemented

The search box performs a case-insensitive substring match across category, subcategory, description, notes, and payment method. This means a search for “class” can find a note, and “bkash” finds the payment method, without a separate mode.

Filters, sorting, and day grouping

Implemented

04 · Feature details

Budgets

Simple limits that answer “Can I still spend?” without requiring a full envelope-budgeting system.

17

Daily and monthly budgets with optional category

Implemented

Each budget has a name, an amount, a period (daily or monthly), and an optional category filter. A budget named “Food & Drinks” with that category only counts food spending; leaving the category empty counts everything.

  • Create: name and positive amount are required; period defaults to monthly.
  • Edit: all fields can change; the original record is updated by ID.
  • Delete: removes the budget without touching transactions; the default daily budget remains in settings.
  • Database support: a month-specific budget column exists and is preserved on edit, but budgets created in the current UI are recurring.
18

Progress states and remaining amount

Implemented

Each card shows spent vs. limit, a progress bar, the percentage used, and the remaining or over-budget amount.

  • On track: below 80% of the limit.
  • Approaching limit: 80–99%, with a caution colour.
  • Budget exceeded: 100% or more, with the over-budget amount.
19

Default daily budget and latest-budget selection

Implemented

The overview card chooses the most recently created budget and respects its period and category. If no budgets exist, it falls back to the profile’s default daily budget (৳300 for a new account).

  • What counts: only transactions at or before “now” — future-dated records do not inflate spending.
  • Daily budgets: count the selected day; monthly budgets count the selected month.
  • Category budgets: count only that category, so a food budget does not absorb transport costs.
Design choice: budgets are intentionally lightweight. There is no rollover, envelope transfer, or per-week budget in the current model; the period choices are daily and monthly.
04 · Feature details

Finance tools

A hub for the money that is not a simple transaction: loans, recurring bills, shared costs, and monthly review.

The Finance tools page links four tools: Loans & bills, Shared expenses, Monthly summary, and Backup & export. Each opens a focused page with its own header and navigation back to the workspace.

20

Loans to repay and money lent

Implemented

Track two directions: “I need to repay” and “I lent money”. Each record stores the other person, principal, remaining balance, due date, and optional notes.

  • Balance display: remaining and principal, e.g. “৳700 remaining of ৳1,000 · due 2026-12-01”.
  • Independent ledger: loan movements do not change the transaction history or current balance — by design.
  • Editing: changing the principal preserves the amount already paid and recalculates the remaining balance.
21

Partial loan payments and settlement

Implemented

A compact payment field accepts any valid amount up to the remaining balance. On update, the remaining balance drops, and the list refreshes immediately.

  • Validation: positive amount, at most two decimals, never more than what is owed.
  • Settlement: at zero remaining, the reminder is cancelled and the payment field disappears.
  • Reminders: rescheduled against the due date after a partial payment, if notifications are on.
  • Deletion: removes the loan and cancels its scheduled reminder after confirmation.
22

Recurring bills

Implemented

Repeat a bill weekly, monthly, or yearly with a name, amount, category, next due date, and a “remind me one day before” toggle.

  • Monthly dates: the 31st clamps correctly to shorter months; month-end bills stay at month-end.
  • Yearly dates: February 29 becomes February 28 in non-leap years.
  • List view: amount, frequency, next due date, and reminder state.
23

Mark bill paid

Implemented

One action records the expense and moves the bill forward.

  • Expense created: type expense, the bill’s amount and category, description “Bill payment: <name>”, preferred payment method, current timestamp.
  • Next due date: calculated strictly after today, advancing repeatedly if the bill is overdue.
  • Atomic local write: the bill update and the transaction are queued together before syncing.
  • Reminder: rescheduled for the new due date.
24

Shared expense splits

Implemented

Split a cost with people identified only by name — they do not need SpendWise accounts and are not notified.

  • Input: title, total, and comma-separated participants (up to 100 other people).
  • Equal split: the total is divided in integer paisa; any remainder is distributed one paisa at a time, so the shares always sum to the total.
  • Your share: excluded from what others owe you; duplicates and your own display name are rejected.
  • Settlement: each participant can be toggled “Settled” or “Mark settled”; outstanding is owed minus settled.
  • Privacy: the split is a private record in your account, not a shared document.
25

Android local reminders

Implemented

On Android, loans and recurring bills can schedule a device notification for about 9:00 AM the day before the due date.

  • Permission: the app checks and requests notification permission; reminders cannot be scheduled without it.
  • Preference: the global notification switch enables or disables all loan and bill reminders; each bill also has its own toggle.
  • Rescheduling: saving, paying, editing, or deleting a record cancels and re-creates the relevant notification.
  • Boundary: reminders only work in the native Android app; the web build does not deliver notifications, and Android may delay delivery.

Implemented

Backup restore with validation and merge

Implemented

Restore is deliberately strict and non-destructive.

  • Schema validation: checks the format marker, version, record shapes, UUIDs, dates, money limits, and allowed enum values before importing.
  • Account match: the backup’s user ID must equal the signed-in account ID.

  • Sync: added records enter the pending queue and reach Supabase when online.

Implemented

05 · Storage & protection

Data model & security

Six PostgreSQL tables, each owned by exactly one authenticated user and protected by Row Level Security.

Security controls in the code

Row Level Security everywhere

RLS is enabled on all six tables. Select, insert, update, and delete are each governed by auth.uid() = user_id; updates and inserts also use WITH CHECK so a client-supplied owner cannot reassign a record.

Server-assigned ownership

user_id defaults to auth.uid() at the database. Profiles use the auth user ID as their primary key. Ownership never comes from client metadata.

Safe profile trigger

A SECURITY DEFINER trigger with an empty search path creates the profile and copies only the name from sign-up metadata, truncated to 100 characters. Public execute permission is revoked.

Database constraints

Money is numeric(12,2), amounts must be positive, loan remaining cannot exceed principal, enums are checked, and text lengths are bounded. Indexes support owner/date/category queries.

No privileged key in the client

The frontend uses the publishable/anon key only. A service-role or secret key would bypass RLS and is explicitly excluded from the setup instructions.

Validated inputs and files

Transactions and money are validated in the UI and data layer. CSV output guards against formula injection. Backup restore validates structure, IDs, dates, enums, and account ownership before merging.

Money and time correctness

Paisa precision: the client sums integer paisa and rounds only at the boundary. Time zones: daily/monthly boundaries, report dates, and transaction dates use the account’s chosen IANA zone, not the server or browser zone. DST: nonexistent daylight-saving wall times are rejected, while ambiguous fall-back times resolve to one valid offset. Future records: dashboard totals exclude transactions dated after “now”.

06 · Local-first behavior

Offline-first & sync

SpendWise writes locally first, then syncs. The app never blocks an edit on a network request, and it does not show an offline warning.

The write path

Read the local snapshot The account’s IndexedDB state is the source of truth for the current session.
Apply the change locally The new record, edit, or deletion is merged into the snapshot and written back to IndexedDB.
Publish to the UI React state updates immediately, so the dashboard, lists, and totals reflect the change.
Queue the change A pending change with the account ID and operation type is appended to the queue.
Sync when possible If online, the queue is replayed in order through Supabase. Each success removes that change from the queue.
Refresh from the cloud After the queue empties, the app pulls the latest records and profile, then reapplies any remaining pending changes.

Behavior by situation

SituationWhat happens
Online editShown instantly; queued; synced in the background. A toast may confirm the action.
Offline editShown instantly; queued; no offline warning. Data remains available after closing and reopening the app.
Reconnect / app resumedThe online listener, native network listener, or Android app-state listener triggers sync. A 30-second retry runs while changes are pending.
Manual refreshOnline: flushes pending changes, then pulls cloud data. Offline: leaves local data untouched.
Sign outClears the remembered account and in-memory data. The cached snapshot remains on the device unless app data is cleared.
First sign-inRequires internet. Offline access only works after a previous successful sign-in and cache.

Conflict and data-safety boundaries

  • Pending changes win locally: remote data is loaded, then pending operations are reapplied so the local view stays consistent until sync finishes.
  • Account isolation: pending changes carry a user ID and cannot be replayed into a different account.
  • No real-time multi-tab sync: two open tabs do not update each other automatically. Reload or use refresh to see another session’s changes.
  • Not encrypted locally: IndexedDB data and exported backups are plain. Clearing app data removes cached records, including changes that have not synced.

10 · Run it yourself

Quick start

From a fresh clone to a running workspace, plus the commands for the Android build.

Web setup

Install dependencies Node.js 22 or newer, then npm ci.
Create a Supabase project Wait for the database to be ready, then apply the three migrations in order: 20261030000000_initial.sql, 20261030000001_profile_names.sql, 20261104000000_finance_features.sql.
Add environment variables Create .env.local with NEXT_PUBLIC_SUPABASE_URL and NEXT_PUBLIC_SUPABASE_ANON_KEY. Use the publishable/anon key — never a service-role key.
